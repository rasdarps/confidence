PROMPT: ADD READ-ONLY BUSINESS CHAT TO THIS EXISTING POS APP
===========================================================

The POS application already exists. Implement a Business Chat reporting
feature inside its current codebase and architecture. Do not scaffold or
replace the application. First inspect its framework, data model, reports,
permissions, navigation, and existing UI conventions. Use the application's
real data and existing capabilities; do not assume features that are not
present.

IMPORTANT BUSINESS SCOPE
------------------------
This POS handles cash-only sales and purchases. A cash sale may be associated
with a customer, and a cash purchase may be associated with a supplier.

The application does NOT support:
- Credit or partial-payment sales/purchases.
- Customer or supplier outstanding balances, debtors, or creditors.
- Banking features or bank-account reporting.
- Accounting setup, fiscal periods, general ledger, or accounting reports.

Do not add, simulate, or imply any of those unsupported workflows or reports.
In particular, do not show suggested questions such as "customer outstanding
balances", "supplier payments", "bank balances", or "credit sales".
Association with a customer or supplier is a transaction filter, not evidence
of a credit account or debt.

Build chat around existing, verifiable records and report screens. Potential
topics are sales, purchases, sales associated with a customer, purchases
associated with a supplier, product sales, and inventory/expenses only if
those features and their data already exist in this app. Inspect first and
only implement capabilities supported by the target project.


PRODUCT GOAL
------------
Add a built-in conversational reporting screen where an authorized user can
ask plain-language questions about business records and receive a concise,
traceable answer. This is a read-only reporting interface: it must never
create, edit, delete, cancel, pay, or otherwise mutate business records.
Use the existing report data and calculations as the source of truth.

Do not call an external AI service or send business data outside the
application. Prefer a deterministic, testable parser and typed report/query
service that map supported question patterns to explicit report intents,
filters, and date ranges. Do not execute arbitrary SQL, user-provided code,
or natural-language-generated queries.


DISCOVERY BEFORE IMPLEMENTATION
-------------------------------
Before changing files:
1. Identify the sales, purchase, customer, supplier, product, inventory, and
   expense models/tables that actually exist.
2. Inspect the application's existing reports and verify which fields,
   totals, dates, filters, and status rules they use.
3. Confirm how cash sales/purchases and their amounts are represented. Do not
   label invoice totals as money collected unless the data supports that
   claim.
4. Find the existing authentication, roles/permissions, routes, shared
   layout, navigation, CSRF, validation, and throttling patterns.
5. Reuse existing report logic or extract shared query helpers so chat
   answers agree with the report screens. Do not duplicate business
   calculations unnecessarily.
6. Record the supported intents based on verified app functionality. Omit
   unsupported intents rather than creating placeholder behavior.


SUPPORTED QUESTION SHAPES
-------------------------
Implement only those report intents for which the target application has
reliable underlying data. Suitable examples, when supported, include:

- "Total sales today"
- "Sales this week" / "Sales this month"
- "Sales from 2026-09-01 to 2026-09-30"
- "Sales for customer \"Example Customer\" this month"
- "Purchases this month"
- "Purchases for supplier \"Example Supplier\" last month"
- "Best-selling products this month" (only if sale-line data exists)
- "Show current stock" / "Show low stock" (only if stock reports exist)
- "Expenses this month by category" (only if expense data and reports exist)
- Follow-ups such as "And last month?", "Break it down by customer", or
  "Break it down by supplier" only for intents where that grouping is valid.

Customer filters belong to sales. Supplier filters belong to purchases.
Support product/category filters or groupings only if the corresponding
records and report screens support them. Display the question examples
dynamically based on the current user's permissions and the intents actually
implemented.

If a question asks for credit, partial payments, balances owed, bank data,
accounting reports, or any unsupported metric, clearly explain that this
application does not support that report in Business Chat. Do not guess,
silently reinterpret the question, or return a success-shaped zero.


REPORTING RULES AND SEMANTICS
-----------------------------
- Use the same definitions as the corresponding report page: invoice date
  versus payment/transaction date, cancelled/deleted record handling,
  discounts/taxes, quantity units, and total calculations must agree.
- Keep invoice/sales totals distinct from cash received. If this app's
  cash-only model makes those totals equivalent in a particular report,
  confirm that from the implementation before explaining it.
- Filter customer/supplier-tagged records using the actual relationship
  stored on each sale or purchase. Include unassigned records only when the
  user asks for all records; label unassigned rows accurately in breakdowns.
- By default, use the existing report convention for an omitted date (for
  example, today if that is what the report does); state the interpreted
  period in every answer. Do not silently default to all time if the current
  report uses today.
- Interpret "today", "yesterday", "this week", "last week", "this month",
  "last month", "this year", and "last year" using the application's
  configured timezone and established week-start convention.
- Accept explicit dates only in clear, validated formats such as YYYY-MM-DD;
  validate calendar dates and require the start date to be on/before the end
  date.
- Apply filters only where supported by the selected report. If a follow-up
  asks for an incompatible filter or breakdown, return a clarification.
- Do not claim historical snapshots for current stock or other live balances.
  Avoid comparisons for metrics whose historical values are not stored.
- Limit displayed detail rows (for example, to 50), state when rows are
  truncated, and calculate summary totals across all matching records, not
  only the visible rows.
- Clearly show "No matching records" only when a valid supported query
  returned no records. Distinguish that case from errors and unsupported
  questions.
- Include a same-origin link to the relevant existing report/list screen
  where possible. Do not claim that a link reproduces chat filters unless it
  actually does.


ACCESS CONTROL AND DATA SAFETY
------------------------------
- Require authentication and a dedicated Business Chat permission.
- Also require the existing permission for the requested report/data, and
  any existing customer/supplier list permission needed to resolve names.
- Enforce permissions on both the chat page and the query endpoint on the
  server. Hiding a menu item or suggested question is not sufficient.
- Apply existing record-level restrictions (for example, cashier sees only
  their own transactions) to both result rows and aggregate totals.
- Validate and bound input length, conversation identifier, dates, filters,
  and result sizes. Use the framework's safe query builder/ORM and bound
  parameters.
- Throttle the endpoint and use the application's standard CSRF protections.
- Resolve names using exact matches first. If a name is missing, ambiguous,
  or matches multiple records, ask the user to clarify; do not choose a
  guessed record. If record IDs are used, verify access before returning
  data.
- Treat all user text as untrusted. Render it as text, not HTML. Validate any
  result links as same-origin before making them clickable.
- Do not log raw sensitive business data or credentials. Follow existing
  privacy-conscious logging conventions; log query intent, user identity,
  and request ID only when appropriate.
- Return explicit authorization, validation, timeout, and server errors.
  Never suppress failures or return fake zero totals.


CONVERSATION BEHAVIOR
---------------------
- Start with an empty state, a short explanation, and permission-filtered
  sample questions.
- Render user questions separately from report answers.
- Show report title, interpreted date period, active entity filters,
  summary metrics, and a readable table for any returned breakdown.
- Support follow-up questions using a per-user, per-conversation context
  limited to report intent and validated filters/date ranges. Do not store
  unnecessary conversation data or allow one user's context to leak to
  another.
- Provide a New Conversation action that clears the current UI and context.
- Ask a specific clarification when intent, dates, or entity selection is
  ambiguous. Unsupported requests should explain what the chat can answer.
- Show a loading state while querying. Disable duplicate submits while a
  request is in progress, handle timeouts and HTTP errors clearly, and allow
  the user to retry.
- Use accessible live announcements, keyboard-operable controls, visible
  focus states, and responsive layouts consistent with the existing app.
- Add a navigation entry only for authorized users. A floating launcher may
  be used if it matches current app conventions; do not clutter transaction
  entry screens.
- Follow the application's current visual theme. The separate UI theme
  prompt can be applied to styling if it is also provided.


IMPLEMENTATION SHAPE
--------------------
Adapt names and files to the target framework; do not force this exact
structure if the project uses different conventions. Keep responsibilities
separated:

1. A page/controller that authenticates, authorizes, and supplies the
   permission-filtered suggested questions.
2. A deterministic parser that maps supported question patterns to a
   constrained, validated report specification. It should reject mutation
   requests and unsupported report types explicitly.
3. A report service that enforces per-intent permissions and allowed filters,
   executes only known report queries using existing data semantics, and
   returns a typed response.
4. A UI that renders messages and structured report responses safely.
5. Feature tests for authentication, permissions, record scoping, successful
   reports, customer/supplier filters, date boundaries, cancellations or
   deletions, ambiguous entities, unsupported credit/banking/accounting
   questions, mutation requests, and empty results.

Keep response data structured, for example:
- title
- interpreted period
- applied filters
- metrics
- columns and rows
- explanatory notes
- optional same-origin source link

Do not return rendered HTML from the query service. Build the interface from
escaped text and structured data.


TESTING AND DELIVERY
--------------------
- Add focused automated tests using the target project's existing test
  framework and factories/fixtures.
- Verify chat totals match the corresponding existing report for the same
  filters and permissions.
- Verify customer/supplier filters use only the correct transaction type.
- Verify unsupported credit, partial-payment, outstanding-balance, banking,
  and accounting requests return clear clarification and disclose no data.
- Verify unauthorized users cannot access the UI or endpoint and cannot
  bypass role/record restrictions through direct requests.
- Run the smallest relevant test/lint/build commands and report their
  results.
- Summarize the actual supported questions implemented and explicitly list
  any excluded capabilities.

The finished feature should feel like a native part of the existing POS: a
safe, read-only conversational front end to reports the app already supports,
with customer-tagged cash sales and supplier-tagged cash purchases handled as
filters rather than credit accounts.
