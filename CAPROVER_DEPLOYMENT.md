CapRover Single-Image Deployment (Web + Worker + Scheduler)

Overview
- This repository includes a captain-definition and Dockerfile so CapRover can build one image from Git.
- Use the same image for three apps:
  1) mall-pos-web
  2) mall-pos-worker
  3) mall-pos-scheduler

Files Added
- captain-definition
- Dockerfile
- .dockerignore

How to Deploy
1. Create the web app `mall-pos-web` in CapRover.
2. Connect Git and deploy. CapRover will build using captain-definition -> Dockerfile.
3. Set environment variables on web app:
   - APP_ENV=production
   - APP_DEBUG=false
  - APP_URL=https://darppos.backhouse.voltachargegh.com
   - APP_KEY=<same key across all apps>
   - DB_CONNECTION=mysql
   - DB_HOST=<db-host>
   - DB_PORT=3306
   - DB_DATABASE=<db-name>
   - DB_USERNAME=<db-user>
   - DB_PASSWORD=<db-pass>
   - SESSION_DRIVER=database
   - QUEUE_CONNECTION=database
4. Enable deployment hook for web app:
   - php artisan migrate --force
   - php artisan config:clear
   - php artisan cache:clear
   - php artisan config:cache

Database Seeding
- Database migrations run automatically when `RUN_MIGRATIONS=true` (the default).
- The image is currently configured with `RUN_SEEDERS=true` so the first deployment creates the admin account and required default records.
- Immediately after that successful first deployment, set `RUN_SEEDERS=false` in CapRover and redeploy or restart the app. This prevents later deployments from changing default company, product, customer, and supplier records.
- Keep `RUN_SEEDERS=false` for normal production deployments.

HTTPS Behind CapRover
- Set `APP_URL=https://darppos.backhouse.voltachargegh.com` in CapRover.
- The application trusts CapRover's forwarded proxy headers and forces generated URLs to HTTPS when `APP_ENV=production`.

Reuse the Same Image for Worker/Scheduler
Option A (recommended)
- Create `mall-pos-worker` and `mall-pos-scheduler` apps.
- For each app, deploy from Image Name (do not rebuild from Git).
- Use the image tag generated by the latest successful `mall-pos-web` deploy.

Option B
- Connect the same Git repo to worker/scheduler apps as well.
- This will rebuild separately per app.

Worker App Settings
- App: mall-pos-worker
- Public: No
- Start command:
  php artisan queue:work --tries=3 --timeout=90 --sleep=3 --backoff=5 --max-time=3600
- Instance count: start with 1

Scheduler App Settings
- App: mall-pos-scheduler
- Public: No
- Start command:
  php artisan schedule:work
- Instance count: exactly 1

Validation Checklist
- Web app responds on domain.
- `php artisan tinker --execute="dump(config('session.driver')); dump(config('queue.default'));"` shows database/database.
- Jobs are consumed by worker (pending count should not grow indefinitely).
- Scheduled tasks run once (no duplicate scheduler instance).

Tiny Health Check (recommended after each deploy)
- Run inside each app container (web, worker, scheduler):
  - `bash scripts/post_deploy_health_check.sh`
- Run locally on Windows (pre-deploy sanity check):
  - `powershell -ExecutionPolicy Bypass -File scripts/post_deploy_health_check.ps1`
- Expected final output:
  - `health_check=ok`

Notes
- Keep APP_KEY and DB credentials identical across all three apps.
- If worker is down, jobs stay pending in jobs table.
- If scheduler has more than one instance, scheduled tasks may execute multiple times.
