1. EXECUTIVE SUMMARY & ARCHITECTURAL FOUNDATION
--------------------------------------------------------------------------------
This implementation transforms the application into a scalable multi-outlet system 
built on a single unified database. 

A. CENTRAL HQ / CENTRAL WAREHOUSE (The Core Brain):
   - Master Product Catalog: Products, categories, units, barcodes, and pricing.
   - Procurement: All supplier purchases (AP) are received into Central Warehouse.
   - Stock Distribution: Central dispatches inventory to outlets via Stock Transfers.
   - Accounting & Banking: Full Chart of Accounts, General Ledger, Journals, Bank Accounts,
     and Capital/Loans remain 100% centralized.
   - Reporting: Consolidated financial statements (P&L, Balance Sheet, Trial Balance)
     plus per-outlet drill-downs (Sales by Outlet, Stock Valuation by Outlet).

B. RETAIL OUTLETS (Lean Operational Front-Ends):
   - Point of Sale (POS): Sells only from the outlet's locally allocated stock.
   - Stock Receiving: Accepts incoming stock transfer shipments from Central.
   - Daily Cash Close: Reconciles drawer cash at end-of-day for remittance to Central.
   - Access Restrictions: Outlets have ZERO access to Chart of Accounts, General
     Ledger, Banking, Supplier Purchases, or Company Financial Reports.

C. NO LEGACY DATA BACKFILL:
   - Because this is a fresh setup, migrations will be created cleanly.
   - The initial seeders will create the "Central Warehouse / HQ" and assign default 
     administrative users and initial stock directly.


2. DATABASE SCHEMA DESIGN (CLEAN FRESH SETUP)
--------------------------------------------------------------------------------

A. TABLE: `outlets`
   - id                     : bigint, PK
   - name                   : string(100) (e.g., "Central Warehouse", "Airport Branch")
   - code                   : string(20), unique (e.g., "HQ-CENTRAL", "OUT-001")
   - type                   : enum('central_warehouse', 'retail_outlet')
   - is_central             : boolean, default(false)
   - phone                  : string(30), nullable
   - email                  : string(100), nullable
   - address                : text, nullable
   - is_active              : boolean, default(true)
   - created_by, updated_by, deleted_by : foreign keys to users (nullable)
   - timestamps, softDeletes

B. TABLE: `outlet_stocks`
   (Decouples inventory quantity from the catalog `products` table)
   - id                     : bigint, PK
   - outlet_id              : bigint, FK -> outlets.id (onDelete cascade)
   - product_id             : bigint, FK -> products.id (onDelete cascade)
   - quantity               : decimal(15,2), default(0.00)
   - stock_level            : decimal(15,2), default(0.00) (minimum alert threshold)
   - timestamps
   - UNIQUE KEY (`outlet_id`, `product_id`)
   - INDEX (`outlet_id`, `quantity`)

C. TABLE: `stock_transfers`
   - id                     : bigint, PK
   - transfer_no            : string(50), unique (e.g., "TRF-20261027-0001")
   - from_outlet_id         : bigint, FK -> outlets.id (usually Central)
   - to_outlet_id           : bigint, FK -> outlets.id (destination branch)
   - status                 : enum('draft', 'dispatched', 'received', 'cancelled')
   - transfer_date          : date
   - dispatched_at          : dateTime, nullable
   - received_at            : dateTime, nullable
   - dispatched_by          : bigint, FK -> users.id (nullable)
   - received_by            : bigint, FK -> users.id (nullable)
   - notes                  : text, nullable
   - created_by, updated_by : bigint, FK -> users.id (nullable)
   - timestamps

D. TABLE: `stock_transfer_items`
   - id                     : bigint, PK
   - stock_transfer_id      : bigint, FK -> stock_transfers.id (onDelete cascade)
   - product_id             : bigint, FK -> products.id (onDelete restrict)
   - qty_dispatched         : decimal(15,2)
   - qty_received           : decimal(15,2), default(0.00)
   - unit_cost              : decimal(15,2), nullable (valuation at transfer time)
   - timestamps

E. TABLE MODIFICATIONS (ADDING `outlet_id`):
   - `users`: add `outlet_id` (nullable, FK -> outlets.id). Null = Central / All Outlets.
   - `sales`: add `outlet_id` (not null, FK -> outlets.id).
   - `stock_ledgers`: add `outlet_id` (not null, FK -> outlets.id).
   - `cash_reconciliations`: add `outlet_id` (not null, FK -> outlets.id).
   - `stock_adjustments`: add `outlet_id` (not null, FK -> outlets.id).


3. CENTRALIZED ACCOUNTING & FINANCIAL FLOW
--------------------------------------------------------------------------------
1. Centralized Single Ledger:
   All financial events post into the single, central Chart of Accounts.
   - When an outlet makes a sale:
     * Dr. Cash on Hand (or Accounts Receivable)
     * Cr. Sales Revenue
     * Dr. Cost of Goods Sold (COGS)
     * Cr. Inventory Asset
   - The Journal Entry record is stamped with `outlet_id` so Central can filter
     revenue and profitability by branch while maintaining a single Balance Sheet.

2. Stock Distribution (No Financial Journal Needed):
   - Transferring stock between Central and an outlet is an internal movement.
   - It updates `outlet_stocks` and logs `transfer_out` and `transfer_in` in 
     `stock_ledgers`. 
   - No complex inter-company financial journals are required.

3. Cash Drawer Remittance:
   - At day's end, the outlet closes their drawer via Cash Reconciliation.
   - When cash is remitted/banked into Central's account, Central records a 
     Bank Transaction / Transfer moving funds into the Central Bank Account.

- Create `App\Models\OutletStock`:
  * Relationships: `outlet()`, `product()`
- Create `App\Models\StockTransfer` and `App\Models\StockTransferItem`
- Update `App\Models\Product`:
  * Add `outletStocks()` relationship

- Update `App\Models\User`:

    logs `transfer_in` in `stock_ledgers`, sets status to `received`.
